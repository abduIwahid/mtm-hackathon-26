# Decisions

1. **Model only reads; code plans and validates.** The brief's own hint ("a model where language needs reading, plain code where arithmetic will do") + exactness of figures + the wrong-message catch must be provable, not vibes.
2. **One small model for every call: openai/gpt-oss-20b (Groq).** Small-model bonus (+10) requires every call on the list; 20B is the laptop class. One extraction call for the full pack keeps tokens lean and the run at ~5s of a 120s limit.
3. **Updates: classify (reading) -> quantity scan -> one area extraction.** At most 2 model calls per update (limit 5); only affected areas recomputed; the prediction slip can state this exactly.
4. **Judges used = judges needed (17), not confirmed (20).** The brief's own practice note says 177 people to feed = 150 students + 10 staff + 17 judges; honorarium and food follow the needed count.
5. **Food: standard tier first.** The standard box is the default offering; the basic tier is used only if the budget cannot fit the standard plan.
6. **Standard library only.** No installs at the venue; python3 is enough. State in run/ (git-ignored) so the volunteer's git-status check stays clean.
7. **Transactional updates.** An update is merged into a snapshot-copied candidate state, the plan is rebuilt and all six checks re-run; if any previously-passing check would break, the snapshot is restored (rollback) and the rejection is recorded with its reason. Committed updates append to the session's update history with the budget total after them.
8. **No source-authority weights.** The brief's conflict rule is supersession (latest dated fact wins, arrival order as tiebreak); it never ranks senders. Invented authority weights (e.g. Dean over caterer) could reject a correct update on the unseen pack, so conflicts resolve by date, then arrival, then validation - never by who sent the message.
9. **No model-reported confidence scores.** A confidence number the model assigns to its own extraction decides nothing and verifies nothing; every extracted fact is either validated by the deterministic checks or it does not reach the plan. Provenance (which message, which date) is recorded instead - that is auditable.
10. **Fact ledger over fact database.** Each fact carries its source message number (and date where the message has one); the plan and the UI print the full ledger, so any figure can be traced back to the message that stated it.
11. **Future integration seam (not built).** The system is one command over plain files: a messages file in, run/plan.txt + run/trace.txt + run/state.json out. A future workflow tool (e.g. n8n) can drive exactly that seam - write the file, run the command, read the outputs - with no changes to the planner. No n8n integration is implemented now.
